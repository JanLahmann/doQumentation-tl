Mag-manage ng quantum-centric supercomputing workflow gamit ang QCSC-Prefect

Tantiya ng paggamit: 30 segundo ng QPU time sa isang IBM Quantum® Heron r2 processor. Hindi kasama sa tantiyang ito ang oras sa pila at classical processing. Maaaring mag-iba ang runtime mo.

Mga learning outcome​

  • Subaybayan ang isang quantum-centric supercomputing (QCSC) workflow sa Prefect Cloud, na may isang task bawat yugto ng Qiskit pattern.

  • I-configure ang workflow ayon sa role, na may mga run parameter sa run form ng Prefect Cloud at ang mga setting ng high-performance computing (HPC) at quantum processing unit (QPU) sa mga Prefect block.

  • Ipagpatuloy ang isang bigong run nang hindi inuulit ang QPU job nito, at gamitin muli ang mga sample ng isang run sa bagong run.

Mga kinakailangan​

  • I-set up ang QCSC-Prefect sa isang Slurm cluster, na naghahanda ng Slurm login node, ng mga Python environment, at ng mga IBM Quantum credential.

  • Sample-based quantum diagonalization ng isang chemistry Hamiltonian, na nagpapaliwanag ng algorithm.

Pinagmulan at konteksto​

Pinapatakbo ng isang QCSC workflow ang isang QPU at isang HPC system bilang isang makina. Pinapatakbo ng QCSC-Prefect ang mga QCSC workflow sa Prefect at pinananatili silang masusubaybayan, na-configure, at maipagpapatuloy.

Ipinapakita ng tutorial na ito ang mga feature na ito gamit ang sample-based quantum diagonalization (SQD) ng N2_22​ molecule. Sina-sample ng Quantum Resource Management Interface (QRMI) ang Circuit sa loob ng isang Slurm job. Dina-diagonalize ng eigensolver na Fulqrum ang mga na-sample na subspace sa mas maraming Slurm job. Pinapatakbo ng isang Prefect Cloud deployment ang dalawa.

Nagpapatakbo rin ang QCSC-Prefect ng malalaking QCSC workload, tulad ng sa mga sumusunod na proyekto.

  • Gumamit ng QCSC-Prefect ang isang pag-aaral ng mga protein-ligand complex na may mahigit 12,000 atom. Nag-sample ito ng mga quantum-embedding fragment sa dalawang 156-qubit na IBM Quantum processor, na hanggang 94 na qubit, at dina-diagonalize ang mga fragment subspace sa mga supercomputer na Fugaku, Miyabi-G, at ROQUO [1].

  • Nagpatakbo ang isang pag-aaral ng mga iron-sulfur cluster ng pinalawak na QCSC-Prefect SQD workflow na may 36 na orbital (72 qubit) at subspace dimension na hanggang 3×10103 \times 10^{10}3×1010 sa mga supercomputer na Fugaku, Miyabi, at ROQUO [2].

Ang hamon ng mga QCSC workflow​

Tipikal ang SQD workflow sa mga QCSC workload. Sinasagot ng QCSC-Prefect ang bawat hamon nito gamit ang isang feature, tulad ng sa sumusunod na talahanayan.

HamonFeature ng QCSC-Prefect
Sumasaklaw ito ng ilang resource. Hawak ng isang Slurm job ang QPU, tapos maraming Slurm job ang nagdi-diagonalize ng mga subspace, round after round.Masusubaybayang workflow
Maraming parameter ito sa iba't ibang antas (agham, Circuit, at cluster), at dapat nasa labas ng lahat ng ito ang mga credential.Mga na-configure na parameter
Mahaba ito at maaaring pumalya kahit saan, mula sa walltime limit, pagkabigo ng node, o mahabang pila sa QPU. Kung walang ingat, ang huling pagkabigo ay nangangahulugang magsa-sample ulit sa QPU.Maipagpapatuloy na execution

Ang bawat hakbang ng Qiskit Pattern sa QCSC-Prefect, hakbang-hakbang ay nagtatapos sa isang kahon na nagpapakita kung paano sinusubaybayan, kino-configure, at ipinagpapatuloy ng QCSC-Prefect ang yugtong iyon.

Masusubaybayang workflow​

Ang Prefect flow ay isang Python function na binubuo ng mga task. Ginagawa ng QCSC-Prefect na isang task ang bawat yugto ng isang Qiskit pattern (Map, Optimize, Execute, at Postprocess). Para sa bawat run, ipinapakita ng Prefect Cloud ang sumusunod na impormasyon:

  • Ang task graph, na may arrow saanman ipinapasa ng isang task ang resulta nito sa iba.

  • Ang state, mga input, mga log, at tagal ng bawat task, na mafi-filter ayon sa mga stage tag na map, optimize, execute, at post-process.

  • Ang mga artifact, na mga talahanayan at link na ini-publish ng mga task, tulad ng pinagmulan ng mga sample o ang enerhiya ng bawat subspace.

Nagsusumite at nagmo-monitor lang ng gawain ang workflow host. Ang compute-intensive na gawain ay tumatakbo bilang mga Slurm job, tulad ng sa sumusunod na larawan.

Maipagpapatuloy na execution​

Iniimbak ng Prefect ang mga resulta ng unang tatlong yugto kasama ng flow run. Kung pumalya ang isang susunod na task, ang Retry sa flow run ay gumagamit muli ng mga nakaimbak na resulta at pinapatakbo lang ang pumalya, tulad ng sa sumusunod na larawan.

Maaari ring mag-load ang bagong run ng mga sample ng naunang run sa halip na mag-sample, dahil itinatala ng Execute stage kung nasaan ang mga sample nito.

Sulyap sa SQD​

Nagsa-sample ang SQD ng mga bitstring mula sa isang local unitary cluster Jastrow (LUCJ) circuit na binuo mula sa coupled cluster singles and doubles (CCSD) amplitude, inaayos ang mga bitstring na sinira ng noise (configuration recovery), at dina-diagonalize ang Hamiltonian sa mga subspace na sakop ng mga na-sample na configuration [3]. Ipinapaliwanag ng SQD tutorial ang algorithm. Sa QCSC-Prefect, ang SQD ay ang flow na sqd, na may sumusunod na task graph.

YugtoTaskInput mula sa ibang task
Mapcompute_molecular_integralsWala
Optimizeget_lucj_paramsMga integral mula sa Map
Executequantum_sampling, na may build_lucj_circuit sa loob nitoMga LUCJ parameter mula sa Optimize
Postprocesssqd_loopMga integral mula sa Map, at mga sample mula sa Execute

Kapag gumagamit muli ng mga sample ang isang run, pinapalitan ng load_qrmi_result (o load_runtime_job para sa mga sample mula sa IBM Quantum Platform) ang parehong get_lucj_params at quantum_sampling, kaya walang Optimize task ang run. Sa random mode (Quantum Source na nakatakda sa random), walang Optimize o Execute task, at direktang nagpapakain ang Map sa sqd_loop.

Ang halimbawa ay ang N2_22​ sa bond length na 1.1 A˚\AAA˚ sa 6-31G basis, na naka-freeze ang dalawang 1s core orbital. Nag-iiwan ito ng 16 na spatial orbital na may limang α\alphaα at limang β\betaβ na electron, na isang 32-qubit na Circuit.

Itakda ang mga variable ng setup guide, i-activate ang ~/venv/qcsc-host, at i-install ang SQD workflow at ang Fulqrum integration.

I-install ang Fulqrum solver sa isang compute node​

Magbukas ng shell sa isang compute node. Ipinapasa ng srun ang mga variable ng shell ng workflow host sa compute node.

# Run in a terminal on the workflow host.

Tina-transpile ng QRMI worker ang Circuit sa compute node gamit ang SQD transpilation hook, na Qiskit lang ang ini-import. Idagdag ang hook sa ~/venv/qcsc-node at suriin ang mga import. Walang ipinapakita ang command na python kapag nagtagumpay ang mga import.

I-build ang Fulqrum at qcsc-fulqrum-solve sa sarili nilang environment, packages/qcsc-prefect-fulqrum/native/fulqrum. Nangangailangan ang build ng C++ compiler na may OpenMP. Ang FULQRUM_WITH_PRIMME=1 ay nagbi-build din ng PRIMME eigensolver, na nangangailangan ng C compiler, mga Python header, pkg-config, at isang BLAS at LAPACK library na may .pc file.

realpath packages/qcsc-prefect-fulqrum/native/fulqrum/bin/qcsc-fulqrum-solve

Itala ang naka-print na path, dahil ito ang tinuturo ng mga solver block. Ibinabalik ka ng exit sa workflow host. Para sa mga build option, tingnan ang Fulqrum integration.

Tandaan ang sumusunod na mga punto kapag ine-edit ang file.

  • Isulat nang buo ang mga path, dahil hindi nag-e-expand ng mga environment variable ang file. Gumagana ang karakter na ~. Panatilihin ang bawat top-level key, tulad ng python_executable, bago ang unang table header.

  • Hindi na kailangang baguhin ang [qrmi] table, dahil ang qrmi-runtime block ang nagbibigay ng instance at ng QPU. Itakda lang ang resource para i-override ang Backend. Nananatili ang mga credential sa qrmi_config.json, hindi sa file na ito.

  • Hawak ng slurm profile ang mga setting ng scheduler at resource ng isang generic na Slurm cluster, at ino-override ito ng anumang key sa file mo. Itinatakda ng naka-comment na [sqd_advanced] table ang sqd-advanced-settings block, itinatakda ng naka-comment na [advanced] table ang mga pangalan ng block at timeout, at hawak ng table ng bawat solver ang tuning nito. Para piliin ang mga node, rank, at thread ng mga solver job, tingnan ang Size the SQD diagonalization for your HPC resources.

  • May walltime na 12 oras (#SBATCH --time) ang QRMI job at bawat solver job, at naghihintay ang flow nang hanggang 13 oras (timeout_seconds = 46800) para sa bawat job. Para baguhin ang walltime, itakda ang walltime sa itaas ng file para sa mga solver job, o sa [qrmi] table para sa QRMI job, halimbawa walltime = "02:00:00". Ang mas maikling walltime ay maaaring magsimula nang mas maaga sa abalang cluster.

Ang sqd-deploy ang nagse-serve ng flow mula sa workflow host at kumukuha ng mga run na sinimulan mo sa Prefect Cloud, kaya panatilihing bukas ang terminal habang pinapatakbo ang workflow. Qiskit Pattern sa QCSC-Prefect, hakbang-hakbang​

Kinukwenta ng mga sumusunod na hakbang ang apat na stage sa notebook na ito gamit ang PySCF, ffsim, Qiskit, Qiskit Runtime, at qiskit-addon-sqd, nang walang Prefect. Tingnan ang SQD tutorial para sa mga detalye ng bawat kalkulasyon.

Hakbang 1: I-map ang mga classical na input sa isang quantum na problema​

Ang Map stage, ang task na compute_molecular_integrals sa workflow, ay ginagawang mga input ng lahat ng susunod na stage ang molecule. Ibinibigay ng Restricted Hartree-Fock (RHF) ang mga molecular orbital, at hindi isinasama ng mga active-space integral ang dalawang frozen na 1s core. Ibinibigay ng CCSD ang mga t2t_2t2​ amplitude ng ansatz, at ang density matrix nito ang nagbibigay ng mga orbital occupancy na nagsisimula ng configuration recovery. Umuulit ang CCSD nang CCSD_MAXITER beses, bawat isa mula sa mga nakaraang amplitude, kaya hindi nakadepende ang resulta sa DIIS history ng unang iteration. Gumagamit ang notebook na ito ng 4 na iteration, at 10 ang sa workflow.

ATOM = "N 0 0 0; N 0 0 1.1"
BASIS = "6-31g"
N_FROZEN = 2
CCSD_MAXITER = 4

mol = pyscf.gto.M(atom=ATOM, basis=BASIS, symmetry=False, verbose=0)
mf = scf.RHF(mol).run()
norb = mol.nao_nr() - N_FROZEN
nelec = (mol.nelec[0] - N_FROZEN, mol.nelec[1] - N_FROZEN)

# Active-space Hamiltonian with the 1s cores frozen
cas = mcscf.CASCI(mf, ncas=norb, nelecas=nelec)
one_body_tensor, core_energy = cas.get_h1eff()
two_body_tensor = ao2mo.restore(1, cas.get_h2eff(), norb)

# CCSD, iterated from the previous amplitudes
ccsd = cc.CCSD(mf, frozen=N_FROZEN)
eris = ccsd.ao2mo()
ccsd.kernel(eris=eris)
for _ in range(CCSD_MAXITER - 1):
    ccsd.kernel(ccsd.t1, ccsd.t2, eris=eris)
t2 = ccsd.t2

occupancies = np.diag(ccsd.make_rdm1())[N_FROZEN:] / 2
initial_occupancies = (occupancies, occupancies)

print(f"norb = {norb}, nelec = {nelec}")
print(f"E(RHF)  = {mf.e_tot:.8f} Ha")
print(f"E(CCSD) = {ccsd.e_tot:.8f} Ha")
norb = 16, nelec = (5, 5)
E(RHF)  = -108.86761837 Ha
E(CCSD) = -109.09392115 Ha
Paano pinamamahalaan ng QCSC-Prefect ang hakbang na ito

Trace: May tag na map ang task na compute_molecular_integrals. Napupunta ang resulta nito sa get_lucj_params at sqd_loop, kaya dalawang arrow ang lumalabas dito sa graph. Ipinapakita ng mga task log ang output ng PySCF.

Configure: Pinipili ng Molecule group ng run form ang problema, bilang FCIDUMP file o bilang geometry at basis. Binabasa ng workflow na ito ang algorithms/open_loop/sqd/data/n2_631g_fc.fcidump, na naka-freeze na ang mga core. Ang bilang ng mga CCSD iteration (CCSD Restarts, 10 bilang default) ay nasa sqd-advanced-settings block.

Resume: Naka-persist ang resulta (compressed/json), kaya nilo-load ito ng Retry sa halip na patakbuhin muli ang PySCF.

Hakbang 2: I-optimize ang problema para sa pag-execute sa quantum hardware​

Ang Optimize stage, ang task na get_lucj_params sa workflow, ay iniaangkop ang ansatz sa QPU bago pa magkaroon ng anumang Circuit. Binubuo ng ffsim ang LUCJ operator mula sa t2t_2t2​ na may mga interaction lang na tinatakbo ng heavy-hex lattice nang walang SWAP Gate. Ito ang mga same-spin na pares ng magkatabing orbital at ang mga opposite-spin na pares sa bawat ikaapat na orbital, hanggang lima sa isang heavy-hex (Heron) na processor. Pagkatapos ay kino-compress ng ffsim ang operator (optimize=True, naka-on bilang default sa workflow) para mas malapit na ma-reproduce ng isang layer ang t2t_2t2​.

N_REPS = 1

pairs_aa = [(p, p + 1) for p in range(norb - 1)]
pairs_ab = [(p, p) for p in range(0, norb, 4)][:5]

lucj_op = ffsim.UCJOpSpinBalanced.from_t_amplitudes(
    t2,
    n_reps=N_REPS,
    interaction_pairs=(pairs_aa, pairs_ab),
    optimize=True,
    options={"maxiter": 50},
)
n_params = ffsim.UCJOpSpinBalanced.n_params(
    norb, N_REPS, interaction_pairs=(pairs_aa, pairs_ab)
)

print(f"Opposite-spin pairs: {pairs_ab}")
print(f"Ansatz parameters: {n_params}")

Hakbang 3: Mag-execute gamit ang mga Qiskit primitive​

Binubuo ng Execute stage, ang task na quantum_sampling sa workflow, ang Circuit (Hartree-Fock state, LUCJ operator, at measurement), it-transpile ito para sa QPU, at sina-sample ito. Una munang tumatakbo ang mga ffsim PRE_INIT pass sa Transpiler at ginagawa nilang mahusay na mga sequence ng native Gate ang mga ffsim Gate. Nagsa-sample ang notebook na ito gamit ang Qiskit Runtime sa ibm_fez. Palitan ang ibm_fez ng Backend na magagamit ng iyong instance. Sa halip, nagsa-sample ang workflow gamit ang QRMI, sa isang Slurm job na may hawak ng QPU.

def correct_electron_fraction(bool_array):
    """Fraction of the bitstrings with the correct numbers of alpha and beta electrons."""
    # The right half of each bitstring is alpha, the left half is beta.
    n_alpha, n_beta = nelec
    valid = (bool_array[:, norb:].sum(axis=1) == n_alpha) & (
        bool_array[:, :norb].sum(axis=1) == n_beta
    )
    return valid.mean()

Paano pinamamahalaan ng QCSC-Prefect ang hakbang na ito

Inihahanda ng workflow host ang Circuit at nagsa-submit ng Slurm job na humihiling ng QPU. Resume: Naka-persist ang mga sample (compressed/pickle), kaya walang bagong QPU job na isinusumite ang Retry. Itinatala ng sqd-sampling-source artifact kung nasaan ang mga sample, kaya magagamit ulit ng bagong run ang mga ito, tulad sa Opsyonal: ipagpatuloy at gamitin muli ang workflow.

Bakit binubuo at tina-transpile ng Execute ang Circuit

Tina-transpile ng QRMI worker ang Circuit sa compute node laban sa kasalukuyang Target ng QPU, kaya ang QRMI Runtime ang may-ari ng transpilation. Inihahanda ng paghahating ito ang mga fault-tolerant na QCSC system, kung saan mabigat na workload ang transpilation ng mga quantum low-density parity-check (LDPC) error-correction Circuit. Kino-cache ng workflow ang mga parameter ng Circuit, hindi ang mga Circuit. Dinidisenyo ng Map at Optimize ang Circuit. Kinukwenta ng Map ang mga CCSD amplitude, at kino-compress ng Optimize ang LUCJ operator gamit ang ffsim.UCJOpSpinBalanced.from_t_amplitudes(optimize=True), na maaaring mas matagal kaysa sa transpilation para sa kasalukuyang QPU. Ine-encode lang ng build_lucj_circuit at ng Transpiler ang mga parameter na ito sa isang ISA Circuit. Iba ang paghahating ito sa karaniwang Qiskit pattern, at ipinapahiwatig nito kung ano ang magiging hitsura ng isang Qiskit pattern sa isang QCSC system.

Hakbang 4: I-postprocess at ibalik ang resulta sa nais na classical na format​

Ang Postprocess stage, ang task na sqd_loop sa workflow, ay nagpapatakbo ng self-consistent na configuration recovery. Sa bawat round, itinatama nito ang mga na-sample na bitstring gamit ang kasalukuyang orbital occupancy, dina-diagonalize ang Hamiltonian sa ilang batch ng mga configuration, at ina-update ang mga occupancy mula sa pinakamahusay na resulta. Pinapatakbo ng susunod na cell ang diagonalize_fermionic_hamiltonian sa parehong sample set na may parehong mga setting. Ang subspace dimension ay ang 1,000,000 determinant ng workflow (1,000 string bawat spin). Gumagamit ang notebook ng dalawang batch bawat round at sampung round, at apat na batch at limang round naman ang sa workflow. Tulad sa workflow, dina-diagonalize ng Fulqrum ang bawat subspace. Isang beses binubuo ng sci_solver_from_integrals ang Fulqrum Hamiltonian at ibinabalik ang sci_solver na tinatawag ng function para sa bawat batch. Isang TrimPolicy, tulad sa SQD tutorial, ang pinagsasama ang pinakamabibigat na string ng mga batch sa isang subspace at dina-diagonalize ito. Sa mga string na higit sa carryover_threshold, itinatago ng policy ang pinakamabigat na kalahati (carryover_ratio=0.5) para sa susunod na round, tulad ng Carryover Fraction ng workflow.

SUBSPACE_DIM = 1_000_000
NUM_BATCHES = 2
MAX_ITERATIONS = 10

policy = TrimPolicy(
    trim_ratio=0.8,
    carryover_threshold=1e-4,
    carryover_ratio=0.5,
)
sci_solver = sci_solver_from_integrals(one_body_tensor, two_body_tensor)

def run_sqd(bool_array, label):
    """Run SQD on the samples, and return the final energy and the energy of each round."""
    round_energies = []

    def callback(results):
        round_energies.append(
            min(result.energy for result in results) + core_energy
        )
        print(
            f"{label}, round {len(round_energies)}: {round_energies[-1]:.8f} Ha"
        )

    result = diagonalize_fermionic_hamiltonian(
        one_body_tensor,
        two_body_tensor,
        bool_array,
        samples_per_batch=1000,
        norb=norb,
        nelec=nelec,
        num_batches=NUM_BATCHES,
        max_iterations=MAX_ITERATIONS,
        policy=policy,
        sci_solver=sci_solver,
        symmetrize_spin=True,
        max_dim=int(np.sqrt(SUBSPACE_DIM)),
        initial_occupancies=initial_occupancies,
        callback=callback,
        seed=np.random.default_rng(24),
    )
    return result.energy + core_energy, round_energies

Paano pinamamahalaan ng QCSC-Prefect ang hakbang na ito

Trace: May tag na post-process ang task na sqd_loop. Tumatanggap ito ng mga sample at ng mga integral, kaya dalawang arrow ang papasok dito sa graph. Ang bawat batch ay isang FulqrumSolverJob call, isang solve_eigenstate task na nagsa-submit ng isang Slurm job na nagpapatakbo ng Fulqrum. Magkakasabay na tumatakbo sa mga compute node ang mga batch ng isang round. Inililista ng sqd-configuration-recovery artifact ang enerhiya at dimension ng bawat subspace sa bawat round.

Configure: Itinatakda ng SQD group ng run form ang subspace dimension, ang bilang ng batch, at ang bilang ng round. Pinapalitan ng Solver Block Override (solver_block_ref) sa run form ang Solver Block ng sqd-advanced-settings para sa isang run, halimbawa ng isang DICE o SBD block. Ang eigensolver (PRIMME), mga thread, at walltime ay nasa sqd-fulqrum-solver block at sa execution profile nito. Nilo-load ng flow ang solver block bago ang anumang stage, kaya pumapalya ang run bago nito magamit ang QPU kung mali ang pangalan ng block.

Resume: Hindi kino-cache ang sqd_loop, pero nagse-save ito ng checkpoint pagkatapos ng bawat round, sa sqd_checkpoints/<flow run id>/ckpt_t00_w0.npz sa ilalim ng work_dir ng solver. Hawak ng checkpoint ang mga occupancy na nagsisimula sa susunod na round at ang pinakamahusay na enerhiya sa ngayon. Sa Retry, tumutuloy ang sqd_loop pagkatapos ng huling nakumpletong round, gamit ang kasalukuyang mga block.

Opsyonal: ipagpatuloy at gamitin muli ang workflow​

I-retry ang bigong run, at gamitin muli ang mga sample nito​

Retry: Ipagpalagay na, sa isang run na may Max Iteration na naka-set sa 10, umabot sa walltime ang isang solver job sa round 5 at pumalya ang sqd_loop. Taasan ang walltime sa exec-sqd-fulqrum-slurm block sa ilalim ng Blocks, pagkatapos piliin ang Retry sa bigong flow run. Nilo-load ng na-retry na run ang mga nakaimbak na resulta ng unang tatlong stage at walang isinusumiteng QPU job. Ang sqd_loop lang ang pinapatakbo nitong muli, gamit ang bagong walltime, at nagsisimula sa round 5 mula sa checkpoint ng round 4. Ipinapakita ng log nito ang [ckpt] RESUME from …: completed 4 step(s), pagkatapos ang SQD iteration 5/10, tulad sa sumusunod na larawan.

Reuse: Kinukwenta muli ng bagong run ang lahat maliban kung ituturo mo ito sa mga naunang sample. Para subukan ang ibang subspace dimension gamit ang parehong mga sample, magsimula ng custom run na may parehong mga parameter, itakda ang Load from QRMI Job Directory (qrmi_result_dir) sa work directory sa sqd-sampling-source artifact ng unang run, at baguhin ang Subspace Dimension. Pinapalitan ng bagong run ang get_lucj_params at quantum_sampling ng load_qrmi_result, na nagbabasa ng mga sample at walang isinusumite sa QPU. Dapat tumugma ang Reset Mitigation sa sqd-advanced-settings sa unang run, dahil ina-apply ito ng reload. Para sa mga sample na kinuha sa pamamagitan ng IQP, itakda na lang ang Load from Qiskit Runtime Job ID (qiskit_runtime_job_id), at ang stage ay load_runtime_job. Binabasa nito ang job gamit ang mga credential ng prefect-qiskit QuantumRuntime block na pinangalanan sa Quantum Runtime Block (reload) (ibm-runner bilang default). Gawin ang block na iyon nang isang beses gamit ang prefect block create quantum-runtime.

Ipagpatuloy ang recovery nang mas maraming round: Magsimula ng custom run na may parehong mga parameter, itakda ang Resume from Checkpoint (resume_checkpoint) sa path sa sqd-checkpoint artifact ng unang run, at taasan ang Max Iteration. Tumutuloy ang bagong run pagkatapos ng mga nakumpletong round, mula sa mga nakaimbak na occupancy at pinakamahusay na enerhiya. Halimbawa, ang checkpoint na may 32 sa 100 round na tapos at Max Iteration na naka-set sa 200 ay tutuloy sa round 33/200. Binabasa ng bagong run ang checkpoint na iyon at isinusulat ang sarili nitong checkpoint, at nalalapat ang mga sumusunod na patakaran.

  • Dapat tumugma sa unang run ang mga sample, ang molecule, Subspace Dimension, Batch Number, at ang uri ng solver (ang bahaging fulqrum_solver_job ng solver block), kaya gamitin muli ang mga sample nito tulad sa Reuse.

  • Maaaring magbago ang pangalan at ang mga job setting ng solver block, tulad ng walltime nito.

  • Kung iba ang isang setting na dapat tumugma, pumapalya ang run bago ang anumang solver job at pinangangalanan ang pagkakaiba.
