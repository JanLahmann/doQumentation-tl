Mga tool para mag-profile, mag-customize, at mag-inspect ng mga experiment

Tantiya ng paggamit: 10 minuto sa isang Heron r2 processor (PAALALA: Tantiya lang ito. Maaaring iba ang runtime mo.)

Para makakuha ng magagandang resulta mula sa quantum computer, kailangan mo ng higit pa sa isang mahusay na dinisenyong circuit. Nakakaapekto sa kalidad ng mga resulta mo ang kasalukuyang kondisyon ng device, kung paano naka-schedule ang circuit mo, ang noise na nararanasan ng circuit, at kung kailan at paano tumatakbo ang job mo sa quantum processing unit (QPU). Nag-aalok ang Qiskit at IBM Quantum® Compute Service ng lumalaking hanay ng mga developer tool na naglalantad ng impormasyong ito. Magagamit mo ang mga tool na ito para kumilos ayon sa impormasyong iyon bago ka gumugol ng QPU time sa buong experiment, at para mag-debug ng natapos na experiment.

Gumagamit ang tutorial na ito ng isang end-to-end na experiment para ipakita kung paano pagsamahin ang mga tool na ito sa bawat yugto ng karaniwang development workflow. Hindi kapaki-pakinabang ang bawat tool sa bawat experiment, kaya piliin ang mga tool na sumasagot sa mga tanong mo tungkol sa sarili mong workload.

Ang workflow ay ang sumusunod:

  1. Maghanda ng mirror circuit ng Trotterized na time evolution ng isang linear na transverse-field Ising model.

  2. Pumili ng backend na may alternatibong calibration data set na dinisenyo para sa mga error mitigation method na nakabatay sa noise model.

  3. Magpatakbo ng mga device benchmarking experiment para gumamit ang transpiler ng napapanahong mga property ng device kapag pumipili ito ng layout.

  4. Suriin ang timing information ng na-schedule na circuit.

  5. Alamin ang mga Pauli-Lindblad at readout noise model para sa circuit.

  6. Magpatakbo ng mga noiseless, unmitigated, at mitigated na lokal na simulation. Ginagamit ng mga noisy na simulation ang natutunang noise model para ipakita kung gaano kalaking pagbuti ang maaari mong makuha mula sa mga napiling error mitigation method. Gumagamit ang tutorial na ito ng probabilistic error cancellation (PEC) at Twirled Readout Error eXtinction (TREX).

  7. Kumuha ng tantiya ng paggamit nang hindi tumatakbo sa QPU, para tingnan kung kailangan mong ayusin ang experiment para magkasya sa budget mo.

  8. Magsimula ng session at mag-trigger ng calibration para gamitin ng experiment ang pinakabagong calibration data.

  9. Patakbuhin ang experiment sa QPU gamit ang Estimator, at ihambing ang mga resulta ng hardware sa simulated na preview.

  10. Suriin ang mga execution span para makita kung may malalaking puwang sa pagitan ng mga grupo ng execution (mga chunk).

Mga kinakailangan​

Bago simulan ang tutorial na ito, tiyaking naka-install ang mga sumusunod:

  • Qiskit SDK v2.3 o mas bago, na may suporta sa visualization

  • qiskit-ibm-runtime v0.52.1 or later (pip install qiskit-ibm-runtime)

  • Qiskit Aer (pip install qiskit-aer)

  • Plotly (pip install plotly)

  • Qiskit Device Benchmarking (pip install git+https://github.com/qiskit-community/qiskit-device-benchmarking.git)

Mga kinakailangan sa plan

Ang ilang hakbang sa tutorial na ito ay hindi available sa bawat plan:

  • Available lang ang mga dry-run job (Mga Hakbang 2.4 at 3.5) sa mga plan na Flex, Premium, at On-Prem.

  • Hindi available ang mga session (Hakbang 4.1) sa Open Plan. Para magpatakbo sa batch mode na lang, itakda ang run_calibration = False sa Hakbang 4.1.

Hakbang 1: Tukuyin ang circuit at observable​

Maghanda ng mirror circuit ng Trotterized na time evolution ng isang linear na transverse-field Ising model. I-mirror ang circuit para kanselahin ang unitary ng circuit at makabuo ng identity circuit. Dahil ang ideal na output ay ang all-zero na state, 1 ang ideal na expectation value ng bawat single-qubit na ZZZ observable. Dinodoble rin ng mirroring ang lalim ng circuit, na nagpapalakas sa epekto ng noise.

import numpy as np
from qiskit.circuit import QuantumCircuit
from qiskit.quantum_info import SparsePauliOp

def construct_ising_circuit(
    num_qubits: int,
    num_trotter_steps: int,
    rx_angle: float,
    barrier: bool = True,
) -> QuantumCircuit:
    circuit = QuantumCircuit(num_qubits)

    for _step in range(num_trotter_steps):
        circuit.rx(rx_angle, range(num_qubits))
        if barrier:
            circuit.barrier()
        for first_qubit in (1, 2):
            for idx in range(first_qubit, num_qubits, 2):
                # equivalent to Rzz(-pi/2):
                circuit.sdg([idx - 1, idx])
                circuit.cz(idx - 1, idx)
        if barrier:
            circuit.barrier()

    return circuit

def mirror_circuit(circuit: QuantumCircuit) -> QuantumCircuit:
    mirror_circ = circuit.copy_empty_like()
    mirror_circ.compose(circuit, inplace=True)
    mirror_circ.barrier()
    mirror_circ.compose(circuit.inverse(), inplace=True)
    mirror_circ.measure_active()
    return mirror_circ
num_qubits = 20
observables = [
    SparsePauliOp("I" * ((num_qubits - 1) - q) + "Z" + "I" * q)
    for q in range(num_qubits)
]

# Free parameters of the demonstration circuit: the number of Trotter steps
# sets the circuit depth, and rx_angle is the transverse-field rotation angle
# applied in each step (pi/4 makes the dynamics non-Clifford)
num_trotter_steps = 5
rx_angle = np.pi / 4

circuit = construct_ising_circuit(
    num_qubits, num_trotter_steps, rx_angle, barrier=False
)
mirrored_circuit = mirror_circuit(circuit)
mirrored_circuit.draw(
    "mpl", fold=-1, scale=0.3, idle_wires=False, measure_arrows=False
)

Hakbang 2: I-optimize para sa pagpapatakbo sa quantum hardware​

2.1 Gumamit ng alternatibong calibration kung naaangkop​

Pana-panahong kina-calibrate ng IBM® ang mga QPU nito para sa mahusay na performance sa pangkalahatang mga use case. Gayunman, may mga workload na nakikinabang sa mga instruction na iba ang pagkaka-tune ng mga parameter. Para sa higit pang impormasyon, tingnan ang Mga espesyal na na-calibrate na instruction.

Gumagamit ang tutorial na ito ng alternatibong calibration data set na tinatawag na slow_gates_ac. May mas mabagal na cz gate ang calibration na ito at minomodulate nito ang two-level system (TLS) bias para patatagin ang mga error ng device sa paglipas ng panahon. Nakikinabang dito ang mga error mitigation method na umaasa sa natutunang noise model. Available lang ang slow_gates_ac calibration sa mga Heron QPU. Kung tatakbo ka sa Nighthawk QPU, gamitin na lang ang slow_gates.

from qiskit_ibm_runtime import QiskitRuntimeService

service = QiskitRuntimeService()
# Use slow_gates_ac because this tutorial uses a noise-learning-based mitigation method
backend = service.backend("ibm_kingston", calibration_id="slow_gates_ac")

2.2 Magpatakbo ng real-time na device benchmarking​

Isa sa pinakakritikal na yugto ng transpilation ang pagpili ng layout, na nagma-map ng mga virtual na qubit sa isang circuit papunta sa mga pisikal na qubit sa target na device. Binabawasan ng magandang layout ang bilang ng mga SWAP operation na kailangan at inilalagay ang circuit sa mga qubit na pinakamahusay ang performance, kaya ang kalidad ng paunang layout ay malaki ang epekto sa kalidad ng mga resulta mo.

May mga pana-panahong benchmarking routine na tumatakbo sa bawat IBM QPU para iulat ang kasalukuyang performance ng mga qubit nito: mga relaxation time (T1T_1T1​), mga coherence time (T2T_2T2​), mga readout error, at mga error ng one- at two-qubit gate. Ginagamit ng Qiskit transpiler ang mga metric na ito sa pagpili ng layout.

Gayunman, ang mga property ng superconducting na qubit ay maaaring mag-drift sa mas maiikling timescale, at ang mga pansamantalang depekto, na kilala bilang mga TLS, ay maaaring pansamantalang magpababa sa isang qubit na maganda ang performance noong oras ng calibration. Kung gumagamit ang transpiler ng lumang impormasyon, hindi nito mapipili ang pinakamahusay na layout. Kaya maaaring sulit na gumugol ng kaunting QPU time para i-characterize ang device bago ka pumili ng layout.

Tingnan ang tutorial na Refresh backend properties with real-time benchmarking para sa detalyadong walk-through. Bumubuo ang characterization suite ng ilang experiment, nagsusumite ng maraming job, at nagfi-fit ng mga resulta. Maaaring tumagal nang ilang minuto ang prosesong ito sa kabuuan. I-enable ang INFO-level na logging para mag-print ang bawat yugto ng progreso nito habang tumatakbo.

import sys
import logging

2.4 I-visualize ang circuit timing​

Bukod sa mga instruction sa isang circuit, baka gusto mo ring i-visualize ang schedule ng circuit, para makita ang idle time sa mga qubit o hindi episyenteng alignment ng mga instruction. Makukuha mo ang pinakadetalyado at pinakatumpak na timing information mula sa IBM Quantum Compute Service sa pamamagitan ng dry-run mode.

Static ang circuit sa tutorial na ito, kaya hindi masyadong informative ang schedule nito. Makakakuha ka ng katulad na timing information nang lokal mula sa circuit at sa mga property ng backend, halimbawa gamit ang timeline drawer na built-in sa Qiskit. Kasama sa tutorial na ito ang hakbang na ito para ipakita kung paano humiling at mag-visualize ng timing information. Pinakamakatulong ang timing information mula sa service para sa dynamic circuits. May mid-circuit measurement, conditional operation, at feedforward ang mga dynamic circuit, na nagdaragdag ng mga implicit operation gaya ng pag-broadcast ng mga resulta ng measurement at pagtukoy ng mga branch. Hindi matutukoy ang timing ng mga operasyong ito mula lang sa circuit at mga property ng backend.

Tingnan ang Visualize circuit timing para sa karagdagang impormasyon. Available lang ang scheduled circuit timing para sa mga Sampler at Executor job, kaya isinusumite ng sumusunod na cell ang circuit sa dry-run mode gamit ang Sampler. Ang mga job na isinumite mo sa dry-run mode ay hindi tumatakbo sa totoong QPU at hindi sinisingil.

Step 3: Mag-apply ng error mitigation at mag-test nang lokal​

3.1 I-Cliffordize ang circuit​

Exponential ang pagtaas ng gastos ng pangkalahatang noisy simulation kasabay ng bilang ng mga qubit, at karamihan sa mga laptop ay hindi kayang mag-simulate ng higit sa humigit-kumulang 32 qubit. Kaya, i-convert muna ang circuit sa isang Clifford circuit, na mas episyenteng mahahawakan ng isang stabilizer simulator. Ni-round ng conversion ang bawat rotation angle sa isang Clifford angle, kaya ang na-simulate na circuit ay tinatantiya lang ang orihinal na circuit at hindi ito eksaktong ginagaya.

from qiskit.transpiler import PassManager
from qiskit_ibm_runtime.transpiler.passes import ConvertISAToClifford

clifford_circuit = PassManager([ConvertISAToClifford()]).run(isa_circuit)
clifford_pubs = [(clifford_circuit, isa_observables)]

3.2 Mag-apply ng PEC gamit ang TREX​

Mahirap minsang pumili ng mga error mitigation method na nagbabalanse ng gastos at katumpakan para sa partikular mong experiment. Magagamit mo ang select-error-mitigation AI agent skill para suriin ang mga available na method para sa workload mo. Nagpapakita ang skill ng summary report na nagpapaliwanag kung napili ba ang bawat method at kung bakit.

Tingnan ang Qiskit AI skills GitHub repository para sa karagdagang impormasyon. Direktang ginagamit ng tutorial na ito ang PEC kasama ang TREX, para makumpleto mo ito nang walang AI agent.

Ang PEC ay isang technique na nagbabawas ng quantum noise kapag kinakalkula mo ang mga expectation value ng mga observable. Sa ideal na kondisyon, makakabuo ang PEC ng unbiased na estimate ng mga expectation value. Natututunan nito ang noise ng bawat layer ng mga two-qubit gate, saka nagpapatakbo ng ensemble ng mga circuit na, sa average, nag-a-apply ng inverse ng noise na iyon. Gumagamit ang PEC ng Pauli twirling para gawing Pauli channel ang noise, na mabisang matututunan at ma-i-invert.

Sa praktika, kasing-tumpak lang ng natutunang noise model ang PEC. Ang sparse Pauli-Lindblad model ay may kasamang one- at two-qubit error term lang sa mga magkatabing qubit, at hindi nito lubos na nakukuha ang mga epekto gaya ng crosstalk sa pagitan ng mga malalayong qubit o mga time-correlated na error. Maaari ring mag-drift ang noise ng device sa pagitan ng noise learning at execution. Hindi kinakansela ng PEC ang noise na hindi nakuha ng model, at sobra ang kompensasyon nito sa noise na sobra ang pagtantiya ng model. Kaya, maaari pa ring lumihis ang mga mitigated na resulta mula sa mga ideal na value sa alinmang direksyon.

Ang TREX ay isang technique na nagbabawas ng mga measurement error, at kapaki-pakinabang kapag tinatantiya mo ang mga expectation value ng mga Pauli observable. Umaasa ito sa measurement twirling, na nagdi-diagonalize sa readout-error transfer matrix at ginagawa itong madaling i-invert. Natututunan ng TREX ang isang rescaling term mula sa diagonal noise channel sa pamamagitan ng pag-measure ng mga twirled calibration circuit na naka-initialize sa zero state. Maaari mong i-enable ang PEC at TREX nang sabay sa pamamagitan ng pagtatakda ng mga Estimator option. Ginagamit ng tutorial na ito ang mga client-side implementation ng mga interface na Qiskit SamplerV2 at EstimatorV2, na ipinakilala sa qiskit-ibm-runtime v0.50.0. Ginagawa ng mga client-side primitive na ito ang karamihan ng pre- at post-processing nang lokal at ipinapasa ang execution sa Executor primitive. Kapag tumatakbo ang mga primitive sa client side, mas malinaw ang nangyayari, mas mabilis ang feedback kapag nagde-debug, at mas pino ang kontrol.

Ipinapatupad ng mga client-side primitive ang parehong API ng mga legacy na server-side primitive. Kaya, kadalasan ay makakalipat ka sa mga client-side primitive sa pamamagitan lang ng pagbabago ng import statement. I-enable ang INFO-level logging para makita ang progress ng client-side pre- at post-processing.

import logging

logger = logging.getLogger("qiskit_ibm_runtime")
logger.setLevel(logging.INFO)
from qiskit_ibm_runtime.executor_estimator import Estimator

estimator = Estimator(mode=backend)
# Enable TREX
estimator.options.resilience.measure_mitigation = True
# Enable PEC
estimator.options.resilience.pec_mitigation = True

3.3 Matuto ng mga noise model at patakbuhin ang Cliffordized na circuit​

Kailangan ng noise learning ng parehong PEC at TREX, na magagawa mo gamit ang NoiseLearnerV3. Ang mga hakbang ay ang sumusunod:

  1. Hanapin ang mga natatanging two-qubit gate layer at measurement layer sa circuit, para sa mga Pauli-Lindblad at TREX protocol, ayon sa pagkakasunod.

  2. Ipasa ang mga layer sa NoiseLearnerV3 para matutunan ang mga noise model.

  3. I-convert ang mga natutunang noise model sa mga Pauli-Lindblad map.

Hindi gumagamit ang Estimator ng pre-learned na TREX noise model. Sa halip, gumagawa ito ng sarili nitong TREX learning. Natututunan pa rin ng sumusunod na code ang dalawang model, dahil ginagamit ng noisy simulation ang natutunang readout model.

Tingnan ang Noise learning helper para sa karagdagang impormasyon tungkol sa NoiseLearnerV3. Bukod sa noise-learning experiment, patakbuhin ang Cliffordized na circuit sa QPU. Hindi laging kailangan ang hakbang na ito, pero nagbibigay ito ng paghahambing para sa mga na-simulate na resulta sa Step 3.4.4. Patakbuhin ang dalawa sa isang batch para mabawasan ang pag-drift ng noise profile sa pagitan nila.

Step 4: Magpatakbo sa hardware​

4.1 Mag-initialize ng session at magpatakbo ng calibration​

Ino-optimize ng QPU calibration ang maraming parameter na tumutukoy sa mga electrical signal na nagpapatakbo sa mga quantum gate at operasyon. Tumatakbo ang mga calibration job sa buong araw sa pagitan ng mga job ng user, pero hindi sa gitna ng aktibong session. Maaaring mag-drift ang mga parameter na ito sa maikling panahon. Para sa pinakamagandang posibleng resulta, isaalang-alang ang pag-trigger ng calibration sa simula ng session, o pana-panahon sa isang matagal na session.

Sa kasalukuyan, readout calibration lang ang suportado, at tumatagal ito ng humigit-kumulang limang minuto ng wall-clock time.

from qiskit_ibm_runtime import Session, Batch, Calibrator

# Set to False to skip the session and calibration and run in batch mode instead
run_calibration = False
mode = Session(backend) if run_calibration else Batch(backend)

if run_calibration:
    calibrator = Calibrator(mode)
    # Wait for calibration to finish before submitting the experiment.
    calibrator.run().result()

4.4 Suriin ang mga execution span​

Kapag nagsumite ka ng mga circuit na may maraming configuration, gaya ng may gate twirling, hindi kinakailangang patakbuhin ng IBM Quantum Compute Service ang lahat ng configuration ng circuit nang sabay-sabay. Sa halip, pinagsasama-sama nito ang mga ito sa mga chunk at nagpapatakbo ng isang chunk bawat shot loop. Ang shot loop ay isang round ng execution sa quantum hardware, kung saan pinapatakbo ang bawat circuit sa chunk para sa hiniling na bilang ng mga shot.

Ang lahat ng job na isinumite sa totoong QPU ay nangangailangan ng ilang classical na pre-processing, gaya ng pag-translate sa mga pulse na maipapadala sa hardware. Dahil maaaring gawin nang parallel ang pre-processing na ito, nagde-dequeue at nagsisimula ang service ng maraming job nang sabay. Gayunpaman, isang unit lang ng trabaho ang kayang iproseso ng QPU sa bawat pagkakataon. Kaya, kung bumubuo ng maraming chunk ang job mo, maaaring maghalo-halo ang mga ito sa mga chunk ng job ng ibang user, at maaaring kailangang maghintay ng bawat chunk ng turn nito sa QPU.

Iniuulat ng metadata ng result ng job ang QPU execution timing para sa bawat chunk. Ipinapakita ng sumusunod na visualization kung may malalaking puwang sa pagitan ng mga execution ng mga chunk sa job mo. Kung mas malapad ang mga puwang kaysa sa kayang tiisin ng experiment mo, maaaring gusto mong patakbuhin ulit ang job, o gamitin ang session execution mode, na nagbibigay sa workload mo ng eksklusibong access sa QPU.

Tingnan ang View execution spans para sa karagdagang impormasyon.

Mga rekomendasyon
  • Patakbuhin ulit ang experiment nang mayroon at walang slow_gates_ac calibration (Step 2.1), ang na-refresh na mga property ng device (Step 2.2), o session calibration (Step 4.1) para masukat kung gaano pinapabuti ng bawat tool ang mga resulta para sa workload mo.
  • Subukan ang mas murang error mitigation method gaya ng zero-noise extrapolation (ZNE), at gumamit ng lokal na simulation at mga dry-run usage estimate para ihambing ang gastos at katumpakan nito sa PEC. Makakatulong sa pagpili ang select-error-mitigation AI agent skill.
  • I-explore ang buong characterization suite, kasama ang randomized benchmarking, sa tutorial na Refresh backend properties with real-time benchmarking.
  • Alamin pa ang tungkol sa mga client-side primitive at sa Executor sa Migrate from server-side to client-side Sampler and Estimator.
  • I-apply ang mga tool na ito sa sarili mong mga experiment. Magsimula sa mga tool na tumutugon sa pinakamalaki mong pinagmumulan ng uncertainty, gaya ng kalidad ng device, noise, gastos, o execution timing.
