Iskay Quantum Optimizer ng Kipu Quantum

Tingnan ang API reference

Tandaan
  • Ang IBM Quantum® Functions ay isang beta feature na available lang sa mga user ng IBM Quantum Premium Plan, Flex Plan, at On-Prem (sa pamamagitan ng IBM Quantum Platform API) Plan. Puwedeng magbago ang mga beta feature.

Pangkalahatang-ideya​

Gamit ang Iskay Quantum Optimizer ng Kipu Quantum, maaari mong harapin ang mga kumplikadong optimization problem gamit ang mga IBM® quantum computer. Ginagamit ng solver na ito ang makabagong bf-DCQO algorithm ng Kipu na nangangailangan lang ng objective function bilang input para awtomatikong maihatid ang mga solusyon. Kayang hawakan nito ang mga optimization problem na may hanggang 156 qubit, na nagbibigay-daan sa paggamit ng lahat ng qubit ng mga IBM quantum device. Gumagamit ang Optimizer ng 1-to-1 na mapping sa pagitan ng mga classical variable at qubit, kaya kayang harapin ang mga optimization problem na may hanggang 156 binary variable.

Ang Optimizer ay nagbibigay-kakayahang lutasin ang mga unconstrained binary optimization problem. Bukod sa karaniwang ginagamit na QUBO (Quadratic Unconstrained Binary Optimization) na formulation, sinusuportahan din nito ang mga higher-order (HUBO) optimization problem. Gumagamit ang solver ng non-variational quantum algorithm na nagpapatakbo ng karamihan ng computation sa mga quantum device.

Nagbibigay ang sumusunod ng mas detalyadong impormasyon tungkol sa algorithm na ginamit at isang maikling gabay sa kung paano gamitin ang function, kasama na ang mga resulta ng benchmarking sa iba't ibang instance ng problema sa iba't ibang laki at kumplikasyon.

Paglalarawan​

Ang Optimizer ay isang ready-to-use na implementasyon ng mga makabagong quantum optimization algorithm. Niresolba nito ang mga optimization problem sa pamamagitan ng pagpapatakbo ng highly-compressed na quantum circuit sa quantum hardware. Nakamit ang compression na ito sa pamamagitan ng pagpapakilala ng mga counterdiabatic term sa pinagbabatayan na time evolution ng quantum system. Nagsasagawa ang algorithm ng ilang iteration ng hardware run para makuha ang mga huling solusyon at pinagsama ito sa post-processing. Ang mga hakbang na ito ay walang putol na isinama sa workflow ng Optimizer at awtomatikong naisasagawa.

Paano gumagana ang Quantum Optimizer?​

Inililahad ng seksyong ito ang mga pangunahing kaalaman ng implemented na bf-DCQO algorithm. Makikita rin ang isang panimula sa algorithm sa Qiskit YouTube channel.

Batay ang algorithm sa time evolution ng isang quantum system na binabago sa paglipas ng panahon, kung saan ang solusyon ng problema ay naka-encode sa ground state ng quantum system sa katapusan ng evolution. Ayon sa adiabatic theorem, ang evolution na ito ay kailangang mabagal para matiyak na nananatili ang system sa ground state nito. Ang pag-digitize ng evolution na ito ang batayan ng digitized quantum adiabatic computation (DQA) at ng kilalang QAOA algorithm. Gayunpaman, ang kinakailangang mabagal na evolution ay hindi praktikal para sa mga lumalagong laki ng problema dahil nagreresulta ito sa pagtaas ng circuit depth. Sa pamamagitan ng paggamit ng mga counterdiabatic protocol, maaaring sugpuin ang mga hindi gustong excitation na nagaganap sa maikling evolution time habang nananatili sa ground state. Dito, ang pag-digitize ng mas maikling evolution time na ito ay nagreresulta sa mga quantum circuit na mas maikli ang depth at may mas kaunting entangling gate.

Karaniwang gumagamit ang mga circuit ng bf-DCQO algorithm ng hanggang sampung beses na mas kaunting entangling gate kaysa DQA, at tatlo hanggang apat na beses na mas kaunti kaysa sa mga standard na QAOA implementation. Dahil sa mas kaunting bilang ng gate, mas kaunting error ang nagaganap sa panahon ng circuit execution sa hardware. Kaya naman, hindi nangangailangan ang optimizer ng paggamit ng mga technique tulad ng error suppression o error mitigation. Ang pag-implement ng mga ito sa mga susunod na bersyon ay maaaring lalo pang mapabuti ang kalidad ng solusyon.

Bagaman gumagamit ng iteration ang bf-DCQO algorithm, ito ay non-variational. Pagkatapos ng bawat iteration ng algorithm, sinusukat ang distribusyon ng mga estado. Ang nakuhang distribusyon ay ginagamit para kalkulahin ang tinatawag na bias-field. Nagbibigay-daan ang bias-field na simulan ang susunod na iteration mula sa energy state na malapit sa dating nahanap na solusyon. Sa ganitong paraan, gumagalaw ang algorithm sa bawat iteration patungo sa mga solusyon na may mas mababang energy. Karaniwang sapat ang halos sampung iteration para mag-converge sa isang solusyon, at sa kabuuan ay nangangailangan ng mas kakaunting iteration kaysa sa mga variational algorithm, na nasa hanay ng halos 100 iteration.

Pinagsasama ng optimizer ang bf-DCQO algorithm sa classical post-processing. Pagkatapos ng pagsukat ng distribusyon ng mga estado, nagsasagawa ng local search. Sa panahon ng local search, random na binabaligtad ang mga bit ng nasukatang solusyon. Pagkatapos ng flip, sinusuri ang energy ng bagong bitstring. Kung mas mababa ang energy, itinatago ang bitstring bilang bagong solusyon. Linearly lamang nag-scale ang local search sa bilang ng qubit; kaya naman, ito ay computationally mura. Dahil itinutuwid ng post-processing ang mga local na bitflip, naitatama nito ang mga bit-flip error na madalas na resulta ng mga imperpeksyon ng hardware at mga readout error.

Mga Benchmark​

Paunawa

Maaaring nakadepende ang performance kapwa sa problem instance at sa mga kasunod na hakbang sa pagproseso. Sa ilang kaso, ang mga classical sample at quantum-generated sample ay maaaring makamit ang magkatulad na huling kalidad ng solusyon matapos ang katumbas na post-processing. Kaya dapat isaalang-alang ng ebalwasyon ang kumpletong optimization workflow.

Ipinapakita ng mga benchmark metric sa ibaba na epektibong tinutugunan ng Optimizer ang mga problemang may hanggang 156 qubit at nagbibigay ng pangkalahatang-ideya ng katumpakan at scalability ng optimizer sa iba't ibang uri ng problema. Tandaan na ang aktwal na mga performance metric ay maaaring mag-iba depende sa mga katangian ng partikular na problema, tulad ng bilang ng variable, density at locality ng mga term sa objective function, at ang polynomial order.

Ang sumusunod na talahanayan ay kinabibilangan ng approximation ratio (AR), isang metric na tinukoy tulad ng sumusunod:

AR=C∗−CmaxCmin−Cmax,AR = \frac{C^{*} - C_\textrm{max}}{C_{\textrm{min}} - C_{\textrm{max}}},AR=Cmin​−Cmax​C∗−Cmax​​,

kung saan ang CCC ay ang objective function, CminC_{\textrm{min}}Cmin​, CmaxC_{\textrm{max}}Cmax​ ang mga minimum at maximum na halaga nito, at C∗C^{*}C∗ ang halaga ng pinakamahusay na solusyong nahanap, ayon sa pagkakasunod. Kaya naman, ang AR=100% ay nangangahulugang nakuha na ang ground state ng problema.

Halimbawa ng custom na configuration​

Narito kung paano mo maaaring i-configure ang Iskay gamit ang iba't ibang setting:

custom_options = {
    "shots": 15_000,  # Higher shot count for better statistics
    "num_iterations": 12,  # More iterations for solution refinement
    "preprocessing_level": 1,  # Light preprocessing for problem simplification
    "postprocessing_level": 2,  # Maximum postprocessing for solution quality
    "transpilation_level": 2,  # Improved transpiler (default)
    "seed_transpiler": 42,  # Fixed seed for reproducible results, which skips the seed search
    "job_tags": ["custom_config"],  # Custom tracking tags
}

Seed optimization: Bilang default, None ang seed_transpiler, at ang transpilation level 2 ay naghahanap sa iba't ibang transpiler seed para mahanap ang circuit na may pinakamagandang depth. Kung magtakda ka ng seed, lalaktawan ng function ang paghahanap na iyon at magiging reproducible ang transpilation.

Mga transpilation level (1-3): Pinipili ng option na transpilation_level ang paraan ng transpilation.

  • Level 1: Karaniwang Qiskit transpiler.
  • Level 2 (default): Pinahusay na transpiler na naghahanap sa 15 transpiler seed at pinapanatili ang pinakamahusay na circuit. Kung itakda mo ang seed_transpiler, lalaktawan ng function ang paghahanap.
  • Level 3: Line routing gamit ang swap strategy para sa linear coupling map na inilalarawan sa Seksyon 2.2.1 ng Weidenfeller et al. Sumusunod ang line routing sa nakapirming swap schedule, kaya linear na lumalaki ang circuit depth nito sa dami ng variable. Para sa mga problemang siksik ang koneksyon, karaniwang gumagawa ang line routing ng mas mababaw na circuit kaysa sa level 1 at 2 at mas mabilis mag-transpile. Sinusuportahan ng Level 3 ang hanggang 127 variable sa mga Heron r2 at r3 processor, 112 variable sa Heron r1, at 120 variable sa Nighthawk.

Inalis ng Version 3.0.0 ang level 0, 4, at 5. Mabibigo ang job na humihiling ng alinman sa mga ito na may error na 1221.

Mga laki ng Function​

Bawat job ay tumatakbo sa isang laki, S, M, o L. Kung masyadong maliit ang laki, tatanggihan ng platform ang job. Kung mas malaki ang laki kaysa sa kailangan ng job, tatakbo ang job sa mas malaking compute profile kaysa sa hinihingi ng gawain. Tingnan ang Mga laki ng Function para sa kung paano gumagana ang mga laki sa pangkalahatan.

Nakadepende ang laki sa dalawang katangian ng iyong model, ang bilang ng mga variable at ang interaction density. Ang interaction density ay ang bahagi ng lahat ng pares ng variable na magkasamang lumalabas sa isang term ng objective o ng isang constraint.

Dapat pumasok ang isang model sa parehong hangganan ng isang laki. Dahil dito, ang maliit na model na maraming interaksyon ay maaaring mangailangan ng L. Halimbawa, ang 10 variable na lahat ay konektado sa isa't isa ay may density na 1.0. Gumagamit ng parehong hangganan ang bawat optimization function, kaya ang isang laki ay may parehong hirap ng model sa bawat function.

May dalawang katangian ng model na nagpapataas ng density nang higit sa inaasahan mo.

  • Ang term na higit sa dalawang variable ay nagdudugtong sa bawat pares ng mga ito. Halimbawa, ang term sa apat na variable ay nag-aambag ng lahat ng anim na pares.

  • Ang constraint ay binibilang bilang penalty na pumapalit dito sa hardware. Ang squared na constraint ay nagdudugtong sa bawat pares ng variable dito, kaya ang one-hot constraint sa apat na variable ay nag-aambag din ng lahat ng anim na pares.

Kung walang hiniling na laki ang job, tatakbo ito sa default na laki, M.

Para mabasa ang mga laki mula sa function mismo, tawagin ang optimizer.sizes(). Para mabasa ang default na laki, tawagin ang optimizer.get_default_size().

Kalkulahin ang laki bago ka magsumite ng job​

Binabasa lang ng calculator ang iyong model at wala nang iba. Walang job na isinusumite at walang nire-reserve, kaya puwede mo itong tawagin nang paulit-ulit habang binabawasan mo ang model para sa mas maliit na laki.

Kailangan ng calculator ang package na qiskit-addon-opt-mapper. Para i-install ito, patakbuhin ang sumusunod na command.

# %pip install qiskit-addon-opt-mapper
"""
Size calculator for the Kipu Quantum ``iskay-quantum-optimizer`` Quantum Function.

IBM's reference ``optimization_size_calculator.py``, with ``to_optimization_problem``
implemented for the ``problem`` dict the function accepts. Everything below that function
is IBM's sizing logic and limits, unchanged, so a size means the same thing across
vendors.

Input:  the ``problem`` dict -- string-encoded index tuples to coefficients, exactly as
        ``validate_problem`` in the function parses them -- plus the other function inputs
        as ``**kwargs``::

            {"()": 1.0, "(0,)": 1.5, "(0, 3)": 2.5, "(0, 1, 2)": 4.0}

Output: ``"S"``, ``"M"`` or ``"L"``, from the number of variables and the interaction
        density: the fraction of variable pairs that appear together in a term of the
        objective or of a constraint.

``problem_type`` ("spin" or "binary") does not change which variables interact, so the
sizing is the same for both.

Constraints are sized as the penalties that replace them on hardware -- see
``_interactions``. Slack variables for inequality penalties are not counted, so a heavily
inequality-constrained model is sized slightly low on the variable count.
https://qiskit.github.io/qiskit-addon-opt-mapper/
"""
from __future__ import annotations

import ast
from collections.abc import Iterator
from itertools import combinations
from typing import Any, Literal

from qiskit_addon_opt_mapper.problems import OptimizationProblem

Size = Literal["S", "M", "L"]

# Limits are provided by IBM
_SMALL_NUMVARS, _SMALL_DENSITY = 50, 0.1
_MEDIUM_NUMVARS, _MEDIUM_DENSITY = 100, 0.25

def calculate_function_size(problem: Any, **kwargs: Any) -> Size:
    """Return the size ("S", "M" or "L") needed to run ``problem``."""
    metrics = _measure(problem, **kwargs)
    if _is_small(metrics):
        return "S"
    if _is_medium(metrics):
        return "M"
    return "L"

def to_optimization_problem(problem: Any) -> OptimizationProblem:
    """Convert the function's ``problem`` dict into an ``OptimizationProblem``.

    Keys are parsed with ``ast.literal_eval``, the same parse the function itself applies,
    so anything the function would reject raises here too rather than being sized on a
    guess. A term is classified by its distinct indices: none is the constant, one linear,
    two quadratic, three or more a higher-order term of that order.

    Indices are remapped to a dense ``0..k-1`` range, because an index that never appears
    is not a variable and gaps in the numbering must not dilute the interaction density.
    """
    if isinstance(problem, OptimizationProblem):
        return problem
    if not isinstance(problem, dict):
        raise NotImplementedError(
            f"cannot size a {type(problem).__name__}: iskay-quantum-optimizer takes a "
            "dict of string-encoded index tuples to coefficients"
        )

    terms = _parse_terms(problem)
    indices = sorted({i for support in terms for i in support})
    index_of = {index: position for position, index in enumerate(indices)}

    linear: dict[int, float] = {}
    quadratic: dict[tuple[int, int], float] = {}
    higher_order: dict[int, dict[tuple[int, ...], float]] = {}
    for support, coefficient in terms.items():
        mapped = tuple(index_of[i] for i in support)
        if len(mapped) == 1:
            linear[mapped[0]] = coefficient
        elif len(mapped) == 2:
            quadratic[mapped] = coefficient
        elif len(mapped) >= 3:
            higher_order.setdefault(len(mapped), {})[mapped] = coefficient

    converted = OptimizationProblem()
    converted.binary_var_list(len(indices), name="x")
    converted.minimize(
        constant=terms.get((), 0.0),
        linear=linear or None,
        quadratic=quadratic or None,
        higher_order=higher_order or None,
    )
    return converted

def _parse_terms(problem: dict) -> dict[tuple[int, ...], float]:
    """Map each term's sorted, distinct indices to its coefficient.

    Repeated supports (for example, "(0, 1)" and "(1, 0)") are summed; for sizing only the
    presence of the term matters.
    """
    terms: dict[tuple[int, ...], float] = {}
    for key, coefficient in problem.items():
        parsed = ast.literal_eval(key) if isinstance(key, str) else key
        if not isinstance(parsed, tuple):
            raise ValueError(f"problem key {key!r} is not a tuple")
        support = tuple(sorted(set(parsed)))
        if any(not isinstance(i, int) for i in support):
            raise ValueError(f"problem key {key!r} holds non-integer indices")
        terms[support] = terms.get(support, 0.0) + float(coefficient)
    return terms

def _measure(problem: Any, **kwargs: Any) -> dict[str, float]:  # pylint: disable=unused-argument
    """Return the number of variables and the interaction density."""
    model = to_optimization_problem(problem)
    num_vars = model.get_num_vars()

    pairs = set()
    for term in _interactions(model):
        pairs.update(frozenset(pair) for pair in combinations(set(term), 2))

    max_pairs = num_vars * (num_vars - 1) // 2
    return {
        "num_vars": num_vars,
        "density": len(pairs) / max_pairs if max_pairs else 0.0,
    }

def _interactions(problem: OptimizationProblem) -> Iterator[tuple[int, ...]]:
    """Yield the variable tuple of every term that couples two or more variables.

    Objective terms contribute their own variables; a linear objective term couples
    nothing.

    A constraint contributes the whole support of its left-hand side, because the
    unconstrained form of the model replaces it with a penalty ``w * lhs**2``, and
    squaring a sum couples every pair of variables in it -- a one-hot constraint over four
    variables becomes a clique on those four. Neither the penalty weight nor the
    right-hand side changes which pairs exist, so neither is needed here. This holds
    whether or not the function handles constraints natively, because a size has to mean
    the same thing across every optimization function.
    """
    objective = problem.objective
    yield from objective.quadratic.to_dict()
    for expression in objective.higher_order.values():
        yield from expression.to_dict()

    for constraint in problem.linear_constraints:
        yield _constraint_support(constraint)
    for constraint in problem.quadratic_constraints:
        yield _constraint_support(constraint)
    for constraint in problem.higher_order_constraints:
        yield _constraint_support(constraint)

def _constraint_support(constraint: Any) -> tuple[int, ...]:
    """Return every variable appearing in a constraint's left-hand side."""
    variables = set(constraint.linear.to_dict())
    if hasattr(constraint, "quadratic"):
        for term in constraint.quadratic.to_dict():
            variables.update(term)
    if hasattr(constraint, "higher_order"):
        for expression in constraint.higher_order.values():
            for term in expression.to_dict():
                variables.update(term)
    return tuple(variables)

def _is_small(metrics: dict[str, float]) -> bool:
    """Determine if the metrics fit T-size 'S'."""
    return (
        metrics["num_vars"] <= _SMALL_NUMVARS
        and metrics["density"] <= _SMALL_DENSITY
    )

def _is_medium(metrics: dict[str, float]) -> bool:
    """Determine if the metrics fit T-size 'M'."""
    return (
        metrics["num_vars"] <= _MEDIUM_NUMVARS
        and metrics["density"] <= _MEDIUM_DENSITY
    )

Halimbawa 1: Simpleng cost function​

Isaalang-alang ang cost function sa spin formulation:

C(x0,...,x6)=3+x0−x1+2x2+x3−2x4+x5−x6+2x0x1−x1x2C(x_0, ..., x_6) = 3 + x_0 - x_1 + 2x_2 + x_3 - 2x_4 + x_5 - x_6 + 2x_0x_1 - x_1x_2C(x0​,...,x6​)=3+x0​−x1​+2x2​+x3​−2x4​+x5​−x6​+2x0​x1​−x1​x2​

where (x0,...,x6)∈{−1,1}7(x_0, ..., x_6) \in \{-1, 1\}^7(x0​,...,x6​)∈{−1,1}7.

Ang solusyon sa simpleng cost function na ito ay

Halimbawa 2: MaxCut​

Maraming graph problem tulad ng MaxCut o Maximum independent set ang mga NP-hard na problema at mga ideal na kandidato para sa pagsubok ng mga quantum algorithm at hardware. Ipinapakita ng halimbawang ito ang paglutas ng MaxCut problem ng isang 3-regular graph gamit ang Quantum Optimizer.

Para patakbuhin ang halimbawang ito kailangan mong i-install ang networkx package bukod sa qiskit-ibm-catalog. Para i-install ito, patakbuhin ang sumusunod na command:

# %pip install networkx numpy

1. Likhain ang objective function​

Magsimula sa paglikha ng random 3-regular graph. Para sa graph na ito, tinutukoy natin ang objective function ng MaxCut problem.

import networkx as nx

# Create a random 3-regular graph
G = nx.random_regular_graph(3, 10, seed=42)

# Create the objective function for MaxCut in Ising formulation
def graph_to_ising_maxcut(G):
    """
    Convert a NetworkX graph to an Ising Hamiltonian for the max-cut problem.
    Args:
        G (networkx.Graph): The input graph.
    Returns:
        dict: The objective function of the Ising model
    """
    # Initialize the linear and quadratic coefficients
    objective_func = {}
    # Populate the coefficients
    for i, j in G.edges:
        objective_func[f"({i}, {j})"] = 0.5
    return objective_func

objective_func = graph_to_ising_maxcut(G)

Kalkulahin ang function size para sa problemang ito.

size = calculate_function_size(objective_func)
print(size)

Ang output ay L. May 10 node at 15 edge ang graph, kaya 15 sa 45 pares ng variable ang nag-iinteract. Ang density na humigit-kumulang 0.33 ay mas mataas kaysa sa hangganan ng M.

2. Patakbuhin ang Optimizer​

Lutasin ang problema sa pamamagitan ng pagpapatakbo ng optimizer.

options = {"shots": 5000, "num_iterations": 5, "use_session": True}

arguments = {
    "problem": objective_func,
    "problem_type": "spin",
    "backend_name": backend_name,  # such as "ibm_fez"
    "options": options,
    "function_size": size,
}

job = optimizer.run(**arguments)

3. Kunin ang resulta​

Kunin ang resulta at i-map ang solution bitstring pabalik sa mga orihinal na node ng graph.

repo = "Kipu-Quantum-GmbH/benchmark-instances"

file = repo.get_contents(urllib.parse.quote(path), ref=branch)

# load json file with benchmark problem
