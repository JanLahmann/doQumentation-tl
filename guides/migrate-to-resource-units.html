Lumipat sa resource units (RUs) sa IBM Quantum Compute API

Sinusukat na ngayon ng IBM Quantum® Platform ang paggamit sa resource units (RUs). Ang RU ay ang unit na ginagamit ng IBM Quantum para sukatin at singilin ang paggamit ng lahat ng workload. Bago ang pagbabagong ito, sinusukat ng platform ang paggamit bilang QPU time sa segundo o millisecond. Para sa higit pang impormasyon tungkol sa mga RU, tingnan ang Resource units.

Sa ngayon, nagbabalik ang API ng dalawang set ng field: ang mga lumang time field at ang mga bagong RU field. Patuloy na gagana ang integration mo. Sa susunod na release, aalisin ng IBM Quantum ang mga time field. Palitan na ngayon ang integration mo para basahin ang mga RU field.

Ginagamit ng gabay na ito ang mga sumusunod na termino:

  • Workload: Isang job, isang session, isang batch, o isang pagpapatakbo ng function.

  • QPU workload: Isang job, isang session, o isang batch. Ang QPU workload ay tumatakbo lamang sa isang QPU.

  • Function workload: Isang pagpapatakbo ng function. Ang function workload ay maaaring gumamit ng classical compute at execution license, at maaari rin itong gumamit ng QPU.

  • Session: Isang grupo ng mga job na sabay na tumatakbo sa isang QPU.

  • Instance: Isang service instance. Ito ang may-ari ng mga workload at may mga limitasyon sa paggamit.

  • Plan: Ang service plan ng isang account. Itinatakda nito ang mga limitasyon sa paggamit para sa lahat ng instance sa account.

tala

Ginagamit ng gabay na ito ang bersyon 0.57.2 ng OpenAPI spec.

Ang value ng header na IBM-API-Version ay dapat 2026-04-15 o isang mas bagong suportadong bersyon ng API.

Ibinibigay ng mga sumusunod na seksyon ang mga detalye para sa bawat endpoint.

Mga Job​

Mga endpoint: GET /v1/jobs at GET /v1/jobs/{id}/metrics.

BalewalainBasahin na lang
usage.qpu_charge_time_secondsusage.value

Ang object na usage ay mayroon ding mga sumusunod na field:

  • usage.unit: Ang unit ng usage.value. Palaging "resource_units" ang value.

  • usage.status: Ang billing status. Ang value ay "pending" o "complete". Kung "pending" ang status, maaari pang baguhin ng platform ang value. Huwag gamitin ang pending na value bilang pinal na paggamit.

  • usage.details[]: Ang paggamit para sa bawat billing metric. Ang value ng bawat entry ay nasa RUs.

Example:

"usage": {
  "qpu_charge_time_seconds": 15,  // old field: disregard
  "value": 0.250005,              // new field: read this
  "unit": "resource_units",
  "status": "complete",
  "details": [
    { "value": 0.250005, "unit": "resource_units", "metric": { "id": "…", "value": 15 } }
  ]
}

Ang field na usage.details[].metric.value ay hindi ang paggamit sa RUs. Ito ang dami ng metric na ginamit ng platform para kalkulahin ang mga RU. May sariling unit ang bawat metric. Halimbawa, segundo ang unit ng isang QPU metric. Para sa paggamit, basahin ang usage.details[].value.

Mga Workload​

Endpoint: GET /v1/workloads.

Ang bawat item sa workloads[] ay may object na usage. Ang object na ito ay may parehong mga field gaya ng object na usage ng isang job.

BalewalainBasahin na lang
workloads[].usage.qpu_charge_time_secondsworkloads[].usage.value

Kung tumatakbo pa ang isang workload, null ang usage.

Mga function workload​

Ang paggamit ng isang function workload ay nasa RUs, gaya ng sa QPU workload. Ang isang function workload ay maaaring gumamit ng higit sa isang metric:

  • Paggamit ng QPU. Sinusukat ito bawat segundo ng quantum time. Tingnan ang Execution modes.

  • Paggamit ng classical compute. Sinusukat ito bawat segundo ng classical time.

  • Gastos ng execution license. Sinusukat ito bawat workload, batay sa laki ng problemang ipinasa sa isang function.

Kino-convert ng platform ang dami ng bawat metric sa RUs. Kaya, lahat ng usage value ay nasa RUs:

  • Ang usage.value ay ang paggamit ng workload, sa RUs.

  • Ang usage.details[].value ay ang paggamit para sa isang metric, sa RUs.

  • Ang usage.details[].metric.value ay ang dami ng metric, sa unit ng metric na iyon. Hindi ito nasa RUs.

Kung magpapakita o magdadagdag ka ng mga usage value, gamitin ang usage.value at usage.details[].value. Huwag gamitin ang usage.details[].metric.value.

Mga Session​

Mga endpoint: POST /v1/sessions at GET /v1/sessions/{id}.

BalewalainBasahin na lang
elapsed_time (segundo)usage.value

Ang object na usage ng session ay may unit at details[]. Gumagana ang mga field na ito gaya ng sa object na usage ng job, maliban sa field na status, na wala sa mga session.

Hindi nagbabago ang mga field na interactive_ttl, max_ttl, at active_ttl. Mga time limit ang mga ito (ang TTL ay nangangahulugang "time to live"), hindi paggamit. Nananatiling segundo ang unit nila.

Mga service instance sa Resource Controller API​

Ang IBM Cloud® Resource Controller API ay isang hiwalay na API. Ginagamit mo ito para gumawa at mag-update ng mga service instance. Kung gumagawa o nag-a-update ka ng mga instance gamit ang API na ito, palitan mo rin ang mga parameter ng instance.

Kapag gumawa o nag-update ka ng instance, ipadala ang mga sumusunod na parameter sa request:

Huwag ipadalaIpadala na langUri ng bagong parameter
instance_limit_secondsinstance_limit_ruNumber o null
usage_allocation_secondsusage_allocation_ruNumber o null

Ito ang kahulugan ng mga parameter:

  • Instance limitAng pinakamataas na paggamit para sa instance. Kung hindi ka magpapadala ng limitasyon sa Open Plan, ang default ay ang katumbas na RU ng 10 minuto.

  • Usage allocation: Ang bahagi ng paggamit para sa instance. Ginagamit ng fair-share scheduler ang value na ito para itakda ang priyoridad ng instance sa pila. Hindi nalalapat ang allocation sa mga Pay-As-You-Go na instance.

Kapag nagbasa ka ng instance, ang object na extensions sa response ay naglalaman ng mga lumang field at mga bagong field. Balewalain ang instance_limit_seconds at usage_allocation_seconds. Basahin ang instance_limit_ru at usage_allocation_ru.

Para sa higit pang impormasyon, tingnan ang IBM Quantum Compute Service REST API documentation.

Analytics ng paggamit​

Mga endpoint: GET /v1/analytics/usage, GET /v1/analytics/usage_grouped, at GET /v1/analytics/usage_grouped_by_date.

Pareho ang mga usage field ng tatlong endpoint. Ibinabalik ng dalawang grouped na endpoint ang mga field na ito para sa bawat grupo o bawat petsa.

Ang mga lumang analytics usage field ay nasa millisecond, hindi segundo.

Bago ang mga function field na ito. Wala silang lumang field sa millisecond:

  • functions_usage_ru

  • avg_functions_usage_ru

  • max_functions_usage_ru

  • functions_classical_usage_ru

  • functions_license_cost_ru

Mas marami ang kasama sa kabuuan sa usage_ru kaysa sa kabuuan sa usage:

  • Ang usage ay ang kabuuan ng QPU time para sa mga session, individual job, at function.

  • Ang usage_ru ay ang kabuuan ng paggamit para sa mga session, individual job, at function. Para sa mga function, kasama rin dito ang classical compute at gastos ng license.

Kaya, ang usage_ru ay hindi lang basta usage sa ibang unit.

Hindi nagbabago ang mga field na queue_time, avg_queue_time, at max_queue_time. Sinusukat nila ang oras ng paghihintay, hindi paggamit. Nananatiling millisecond ang unit nila.

Mga field na hindi nagbabago​

Naglalaman ang mga field na ito ng mga time value, pero hindi sila sumusukat ng paggamit. Walang planong palitan ang mga ito ng IBM Quantum:

  • wait_time_seconds sa mga backend: Ang tinatayang paghihintay sa pila.

  • circuits_execution_time_ns sa GET /v1/jobs/{id}/metrics: Ang oras na tumakbo ang job sa QPU.

  • interactive_ttl, max_ttl, at active_ttl sa mga session.

  • queue_time, avg_queue_time, at max_queue_time sa analytics.

  • rep_times at circuit_duration sa backend configuration.

Mga hakbang sa migration​

  1. Hanapin ang bawat lumang field sa code mo. Hanapin ang qpu_charge_time_seconds, elapsed_time, ang mga field na _seconds sa gabay na ito, at ang mga analytics field sa millisecond.

  2. Palitan ang bawat lumang field ng RU field na nasa mga talahanayan ng gabay na ito.

  3. Kung gumagawa o nag-a-update ka ng mga service instance gamit ang Resource Controller API, ipadala ang instance_limit_ru at usage_allocation_ru. Huwag ipadala ang mga parameter na _seconds.

  4. Palitan ang mga label sa user interface mo. Ipakita ang "RU" o "resource units", hindi "segundo" o "minuto". Huwag i-convert ang mga RU sa oras. Walang takdang rate sa pagitan ng mga RU at oras.

  5. Kung binabasa mo ang usage.details[], gamitin ang value para sa paggamit sa RUs. Huwag gamitin ang metric.value, dahil ang unit nito ay ang unit ng metric.

  6. Kung "pending" ang usage.status, ipakita ang value bilang pansamantala.

  7. Kung nawawala o null ang isang RU field, gamitin ang parehong logic na ginagamit mo ngayon para sa lumang field.
