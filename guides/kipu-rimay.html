Rimay Quantum Feature Extraction - isang Qiskit Function ng Kipu Quantum

Tingnan ang API reference.

tala

Ang Qiskit Functions ay isang experimental na feature na available lang sa mga user ng IBM Quantum® Premium Plan, Flex Plan, at On-Prem (sa pamamagitan ng IBM Quantum Platform API) Plan. Nasa preview release status ito at puwedeng magbago.

Overview​

Pinapalakas ng Rimay ang mga classical machine learning pipeline gamit ang mga feature na nabuo sa quantum hardware. Kumukuha ang function ng classical tabular data at nagbabalik ng set ng mga quantum-transformed na feature. Kapag pinoproseso ng isang quantum system ang data, nakakabuo ito ng mayayamang feature na kumukuha ng mga nonlinear na ugnayan sa pagitan ng mga input. Puwede mong gamitin ang mga nabuong feature nang mag-isa, o kasama ng orihinal mong mga feature, para mag-train ng anumang classical model. Sa maliliit at katamtamang laki ng dataset, puwedeng mapabuti ng mga quantum-transformed na feature ang kalidad ng prediction kumpara sa purong classical na baseline.

Ginawa ang function na ito para sa mga sumusunod na user:

  • Mga data science team na may umiiral na machine learning pipeline sa maliliit at katamtamang laki ng tabular dataset, kung saan huminto na ang pag-angat ng kalidad ng prediction. Idinaragdag mo ang Rimay bilang isang karagdagang preprocessing step, nang hindi ka gumagawa ng anumang quantum circuit.

  • Mga researcher na nag-eexplore ng mga quantum method para sa mga machine learning task.

Paglalarawan​

Pinagsasama ng quantum feature extraction algorithm [1] ang dalawang prinsipyo ng quantum machine learning. Ang una ay ang quantum feature maps, na nag-e-embed ng data sa high-dimensional na Hilbert space kaya mas expressive ang mga representasyong nabubuo. Ang pangalawa ay ang quantum reservoir computing, na gumagamit ng dynamics ng isang quantum many-body system bilang nonlinear na transpormasyon ng input.

Ini-encode ng Rimay ang mga feature value at ang mutual information sa pagitan ng mga feature sa mga local field at coupling coefficient ng isang spin-glass Hamiltonian. Pinapaunlad ng counterdiabatic quantum dynamics ang system papunta sa mga low-energy state nito, na may mga nonlinear na halo ng mga correlation sa input data. Kinukuha ng Rimay ang mga correlation na ito sa pamamagitan ng pagsukat ng single- at two-body expectation value. Ang mga expectation value ang mga quantum-transformed feature na ipapasok mo sa iyong machine learning model.

Workflow​

  1. I-preprocess ang tabular data mo gaya ng gagawin mo sa classical machine learning. Kailangan ng Rimay ng mga numerical feature, kaya i-convert ang mga categorical feature sa numerical, halimbawa gamit ang OneHotEncoder ng scikit-learn.

  2. Hatiin ang data sa training set at test set, at i-upload ang dalawa sa function, tulad ng ipinapakita sa seksyong Halimbawa.

  3. Ginagamit ng Rimay ang training data para buuin ang Hamiltonian na kumakatawan sa data. Bawat feature ay katumbas ng isang qubit, at ang buong training set ang nagpapasya kung aling mga feature, at kaya aling mga qubit, ang nag-iinteract. Sine-save ng Rimay ang istrukturang ito para ma-map nito ang test data at ang mga susunod na inference data gamit ang parehong Hamiltonian.

  4. Para sa bawat sample, itinatakda ng mga feature value ang mga local field ng Hamiltonian, at itinatakda naman ng mutual information sa pagitan ng mga feature ang mga coupling coefficient ng istruktura mula sa hakbang 3. Dini-digitize ng Rimay ang counterdiabatic evolution ng Hamiltonian na ito para maging circuit, at pinapatakbo ang mga circuit sa QPU.

  5. Sinusukat ng Rimay ang mga nagresultang bitstring, saka kinukuwenta ang mga single-body expectation value at ang mga two-body expectation value ng mga qubit na pisikal na magkakabit.

  6. I-download mo ang mga expectation value sa anyong direkta mong maipapasok sa iyong model, o maihahalo sa orihinal mong mga feature.

tala

Dahil sa istrukturang ito, ang bilang ng mga qubit na kailangan ng isang run ay katumbas ng bilang ng mga feature, at ang bilang ng mga circuit na isinusumite nito ay katumbas ng bilang ng mga sample.

Pagkatapos mong mag-fit ng mapping, maaari mong i-map ang bagong data gamit ito, halimbawa para sa inference. Kukunin ng Rimay ang Hamiltonian na ginawa nito habang nag-fit at bubuuin mula rito ang mga circuit para sa mga bagong sample.

Isama ang Rimay sa iyong machine learning pipeline​

Tulad ng sa classical pipeline, magsisimula ka sa pag-preprocess ng raw data, halimbawa sa pamamagitan ng one-hot encoding ng mga categorical feature, at hahatiin ito sa training set at test set. Sa halip na direktang ipasok ang dalawang set sa iyong model, ipapasok mo muna sila sa Rimay, at ita-train mo ang iyong model sa mga quantum-transformed feature.

Mga benchmark​

Ibinenchmark ng Kipu Quantum ang Rimay sa German credit dataset mula sa OpenML [2], na nag-uuri sa 1000 aplikante ng credit bilang mabuti o masamang credit risk. Mayroon itong 13 categorical at pitong numerical na attribute. Ang one-hot encoding ng mga categorical attribute ay nagreresulta sa 48 numerical feature. Itinatabi ng benchmark ang 20% ng mga sample bilang test set.

Bilang baseline, ilang classical model ang na-train sa mga classical feature. Gamit ang Rimay, na-train ang isang random forest sa dalawang paraan: sa mga quantum-transformed feature lang (Random forest Q), at sa mga quantum-transformed feature na sinamahan ng mga classical (Random forest H, para sa hybrid). Ang random forest lang ang nasa talahanayan, dahil ito ang pinakamahusay ang naging performance sa mga quantum-transformed feature.

Mga input​

Ang mode ang nagtatakda kung aling mga parameter ang kailangan ng isang run. Para sa paglalarawan ng bawat input parameter, tingnan ang API reference.

Mga input file​

  • I-upload ang bawat file gamit ang catalog.file_upload() bago mo patakbuhin ang function.

  • Pinapalitan ng isang upload ang anumang naunang file na may parehong pangalan, kahit para sa job na isinumite mo pero hindi pa nagsisimula. Para magpatakbo ng ilang job nang sabay-sabay, bigyan ng sariling pangalan ang mga file ng bawat job, halimbawa run1_x_train.csv at run2_x_train.csv.

  • Ang bawat file ay CSV file na may header row. Ang bawat column ng feature file ay isang feature, at dapat numeric ang bawat value.

  • Ang y_train ay may eksaktong isang numeric na column, na may isang label bawat row ng x_train. I-map ang mga categorical label sa mga numero, halimbawa good at bad sa 1 at 0.

  • Dapat magkapareho ang mga column ng x_test at x_inference at ng x_train, sa parehong ayos.

Itago ang mapping_id at backend_name

Ang mapping_id ang tanging paraan para maabot ang mapping na nabuo ng iyong fit, at hindi ito mahahanap o mababawi. Pinapahintulutan nito ang paggamit ng mapping na iyon, kaya ituring itong credential at huwag ibahagi. Kung mawala mo ito, kailangan mong mag-fit ng bagong mapping, na nangangailangan ng isa pang run sa quantum hardware. Itala rin ang backend_name ng fit, dahil sa processor na iyon lang tumatakbo ang mapping.

Mga limitasyon​

  • Ang bawat feature ay imamapa sa isang qubit, kaya dapat may kahit kasing dami ng qubit ang processor kaysa sa bilang ng feature ng data mo. Kung mas marami ang feature mo, bawasan muna ang mga ito gamit ang feature selection technique.

  • Ang bawat sample ay nagiging isang circuit, at binibilang ng isang run ang training at test sample nang magkasama. Ang isang run ay maaaring maglaman ng hanggang 15,000 sample.

  • Ang isang job ay maaaring humiling ng hanggang 10 milyong execution, kaya ang bilang ng mga sample na minultiply sa shots ay hindi dapat lumampas sa 10 milyon.

  • Dapat matapos ang isang job sa loob ng 24 oras, kasama ang oras na naghihintay ang mga circuit nito sa queue ng processor. Ang job na mas matagal tumakbo ay ihihinto nang walang resulta. Sa busy na processor, panatilihing mas mababa nang malayo sa mga limitasyong ito ang malalaking dataset.

Mga output​

Ang job.result() ay nagbabalik ng dictionary. Ang mga quantum-transformed feature mismo ay isinusulat sa mga CSV file na dina-download mo gamit ang catalog.file_download(). Para sa paglalarawan ng bawat key ng dictionary, tingnan ang API reference. Para sa oras na inabot ng bawat execution phase, tingnan ang Run metadata.

Ang bawat output file ay may isang row bawat input row, sa ayos ng input file, at isang column bawat quantum-transformed feature. Ang mga column na ang pangalan ay nagsisimula sa corr_ ay ang mga two-body expectation value. Walang label column ang mga file. Ang mga label ng training data mo ay nananatili sa iyong y_train file.

Run metadata​

Ang resource_usage ay may isang entry para sa bawat execution phase na dinaanan ng run: "RUNNING: MAPPING", "RUNNING: POST_PROCESSING", at, sa QPU, kadalasan "RUNNING: WAITING_FOR_QPU". Ang bawat entry ay may CPU_TIME, ang wall-clock time ng phase sa segundo, at QPU_TIME, ang QPU time sa segundo. Sa QPU, ang QPU time na siningil ng IBM ay nakatala sa ilalim ng "RUNNING: MAPPING", ang phase kung saan tumakbo ang mga circuit.

Ang "RUNNING: WAITING_FOR_QPU" ay ang oras na naghintay ang mga job mo sa IBM queue. Kinukuha ng run ang oras na ito mula sa mga timestamp ng IBM job, at hindi ito binibilang sa "RUNNING: MAPPING". Kung hindi iniuulat ng IBM ang mga timestamp na iyon para sa bawat job, wala ang entry, at bahagi ng "RUNNING: MAPPING" ang paghihintay.

Tinatapos ng IBM® ang pagkuwenta ng usage nito ilang sandali pagkatapos matapos ang job. Naghihintay ang run nang hanggang halos isang minuto para rito. Ang usage na kinukuwenta pa rin pagkalipas ng oras na iyon ay hindi kasama sa QPU_TIME, at makikita ang pinal na usage sa IBM Quantum Platform. Kung hindi mabasa ng run ang usage mula sa IBM, ang QPU_TIME ay None.

Halimbawa:

Mga laki ng function​

Ang bawat job ay tumatakbo sa isang laki — S, M, o L. Kung masyadong maliit ang tinukoy na laki, tatanggihan ang job. Kung mas malaki ang laki kaysa sa kailangan, tatakbo ito sa mas malaking compute profile kaysa sa hinihingi ng gawain.

Ang laki ng isang Rimay job ay nakasalalay sa bilang ng mga sample na ima-map nito: ang mga row ng x_train at x_test para sa fit-transform, at ang mga row ng x_inference para sa transform. Hindi binibilang ang mga label sa y_train, at walang sample na ima-map ang isang delete run.

Ang bilang ng mga sample lang ang criterion. Walang binabago ang laki maliban sa compute profile: pareho para sa bawat laki ang mga limitasyon sa mga feature, sample, at shots. Ang S at M ay tumatakbo sa parehong compute profile at nagkakaiba sa bilang ng mga sample na sinasaklaw ng bawat isa.

Ang default ay M, na ginagamit kapag walang hiniling na laki ang job. Kaya ang job na may higit sa 9,999 sample ay dapat humiling ng L.

Maaari mo ring basahin ang mapping mula mismo sa function gamit ang rimay.sizes_map, at ang laki kung saan tumatakbo ang isang job kapag wala itong hiniling na laki gamit ang rimay.default_size.

Kuwentahin ang laki bago magsumite​

Patakbuhin ito sa sarili mong mga input. Binabasa lang nito ang mga ito at wala nang iba: walang isinusumiteng job at walang nirereserba, kaya maaari mo itong tawagin nang kasing dalas ng gusto mo.

Ipasa ang mismong mga data set, hindi ang mga pangalan ng file, sa parehong ayos ng input_file, kasama ang mode ng run. Ipinapakita ng Hakbang 2 ng halimbawa ang pagtawag.

from os import PathLike
from typing import Any, Literal, Sequence, Sized

Size = Literal["S", "M", "L"]

# Upper bounds (inclusive) in samples.
_SMALL = 2_999
_MEDIUM = 9_999

FIT_TRANSFORM, TRANSFORM, DELETE = "fit-transform", "transform", "delete"

# Which positions of input_file hold samples, per mode. The labels in
# y_train submit no circuits of their own, so they are not counted.
SAMPLE_POSITIONS = {FIT_TRANSFORM: (0, 2), TRANSFORM: (0,)}

def calculate_function_size(problem: Sequence[Sized], **kwargs: Any) -> Size:
    """Return the size ("S", "M" or "L") required to run the function."""
    metrics = _measure(problem, **kwargs)
    if _is_small(metrics):
        return "S"
    if _is_medium(metrics):
        return "M"
    return "L"

def _measure(problem: Sequence[Sized], **kwargs: Any) -> dict:
    """The samples the job submits."""
    return {"samples": count_samples(problem, kwargs.get("mode"))}

def count_samples(problem: Sequence[Sized], mode: Any) -> int:
    """Rows across the data sets of ``problem`` that carry samples."""
    if mode == DELETE:
        return 0
    if mode not in SAMPLE_POSITIONS:
        raise ValueError(f"cannot size mode {mode!r}")
    if _is_name(problem) or (
        isinstance(problem, (list, tuple))
        and any(_is_name(data) for data in problem)
    ):
        raise TypeError(
            "pass the data, not the file name: read each input_file, e.g. with "
            "pandas.read_csv, and pass the data sets in input_file order"
        )
    if not isinstance(problem, (list, tuple)):
        raise TypeError(
            "pass a list of data sets in input_file order, e.g. [x_train, y_train], "
            f"not a single {type(problem).__name__}"
        )
    return sum(
        len(problem[i]) for i in SAMPLE_POSITIONS[mode] if i < len(problem)
    )

def _is_name(value: Any) -> bool:
    """A file name or path rather than data."""
    return isinstance(value, (str, bytes, PathLike))

def _is_small(metrics: dict) -> bool:
    """Determine if the metrics fit T-size 'S'."""
    return metrics["samples"] <= _SMALL

def _is_medium(metrics: dict) -> bool:
    """Determine if the metrics fit T-size 'M'."""
    return metrics["samples"] <= _MEDIUM

Kung masyadong maliit ang laki, babagsak ang job na may error na 4600 at ang mensahe ay nagsasaad ng laki na dapat gamitin sa halip. Kung mas malaki ito kaysa sa kailangan, normal na tatakbo ang job at magtatala ng 4601 advisory event.

4. I-map ang bagong data​

Pagkatapos mong i-train ang iyong model, i-map ang bagong data gamit ang na-fit na mapping, halimbawa para magpatakbo ng inference. Imamapa ng halimbawang ito ang x_inference.csv, na isinulat ng unang cell ng halimbawang ito. Ipasa ang mapping_id na ibinalik ng fit, para ang mga bagong row ay ma-map gamit ang parehong mapping sa halip na bago.

Ang mapping ay binubuo para sa qubit layout ng isang processor, kaya ipasa ang parehong backend_name ng fit, na ibinalik ng fit sa result["backend_name"]. Huwag gamitin ang least_busy() para piliin ang processor, dahil maaari itong magbalik ng ibang processor. Tinatanggihan ng Rimay ang anumang ibang processor bago ito magsumite ng anuman. Ang bilang ng shot ay galing din sa fit.

catalog.file_upload("x_inference.csv", rimay)

x_inference = pd.read_csv("x_inference.csv")
size = calculate_function_size([x_inference], mode="transform")

job = rimay.run(
    mode="transform",
    input_file=["x_inference.csv"],
    # The processor the mapping was fitted on
    backend_name=fit_backend_name,
    shots=5000,
    mapping_id=mapping_id,
    function_size=size,
)
# Monitor the job status
job.status()
'DONE'
result = job.result()

for file_name in result["output_files"]:
    catalog.file_download(file_name, rimay, target_name=file_name)

5. Burahin ang mapping​

Kapag hindi mo na kailangan ang na-fit na mapping, burahin ito. Ang delete run ay walang ginagawang quantum na gawain, kaya hindi nito kailangan ng processor, shots, o laki ng function. Hindi mo maaaring bawiin ang pagbura. Pagkatapos ng pagbura, wala nang tinutukoy ang mapping_id, at babagsak ang isang transform run na gumagamit nito.

job = rimay.run(mode="delete", mapping_id=mapping_id)
job.result()

Kunin ang mga mensahe ng error​

Kung ang status ng workload mo ay ERROR, gamitin ang job.error_message() para kunin ang mensahe ng error, tulad ng sumusunod:

job = rimay.run(
    mode="fit-transform",
    input_file=["x_train.csv", "y_train.csv"],
    backend_name=backend.name,
    shots=0,
)
job.error_message()

Ang bawat error na iniuulat ng Rimay ay may kasamang code mula sa IBM Quantum error codes, isang mensahe, at isang solusyon na nagsasaad ng value na ipinasa mo at ng value na pinapayagan. Inililista ng sumusunod na talahanayan ang mga pinakakaraniwang error:
